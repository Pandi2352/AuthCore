# Starting a New Project from AuthCore

Step-by-step guide for reusing `authcore-backend` and `authcore-frontend` as the base of a new product (CRM, e-commerce, HRMS, ERP, SaaS, admin panel …).

**What you get for free:** registration, sign-in, sessions, password policies, roles / permissions / groups, user administration, invites, profiles with custom fields, file uploads, activity logs, security emails, metrics — plus the frontend shell and the auth / account screens.

**What you build:** your business modules (leads, products, orders, employees …) on top.

> Example used below: a CRM called **"Nexa CRM"**, slug **`nexa-crm`**. Replace with your own names.

Status markers: ✅ works today · 🔜 available once the frontend module it names is built (until then, do the manual step shown).

## Step 1 — Copy the code ✅

Copy **without** history, dependencies, build output, secrets or uploaded files.

**Windows (PowerShell):**

```powershell
robocopy D:\AuthCore D:\NexaCRM /E /XD .git node_modules dist uploads logs coverage /XF .env .env.local
```

**macOS / Linux / Git Bash:**

```bash
rsync -a --exclude .git --exclude node_modules --exclude dist --exclude uploads \
  --exclude logs --exclude coverage --exclude '.env' --exclude '.env.local' \
  /path/to/AuthCore/ /path/to/NexaCRM/
```

Then start a fresh repository:

```bash
cd NexaCRM
git init
git add .
git commit -m "Start from AuthCore"
```

Optional: rename the folders (`authcore-backend` → `nexa-crm-backend`, `authcore-frontend` → `nexa-crm-frontend`). If you do, update the `paths:` / `working-directory:` / `cache-dependency-path:` entries in `.github/workflows/backend-ci.yml` and `frontend-ci.yml`.

> Want to receive AuthCore improvements later? Instead of a plain copy, keep AuthCore as a second Git remote (`git remote add authcore <url>`) and merge its tags occasionally. Plain copies are simpler; pick one approach and stay with it.

## Step 2 — Rename the backend ✅

```bash
cd authcore-backend          # or your renamed folder
npm ci
npm run project:init -- --name "Nexa CRM" --slug nexa-crm --db nexa_crm \
  --support-email support@nexacrm.com --color "#0f766e" --dry-run
```

Check the dry-run output, then run it again without `--dry-run`. It updates:

| File | Changes |
| --- | --- |
| `project.config.json` | name, slug, description, branding (color, logo, support email, website) |
| `package.json`, `package-lock.json` | package name `nexa-crm-backend` |
| `.env.example` (and `.env` if present) | `APP_NAME`, `MONGODB_URI` database name, `JWT_ISSUER`, `JWT_AUDIENCE`, `REFRESH_COOKIE_NAME`, `MAIL_FROM` display name |

From the slug the backend derives: log service name, metrics prefix (`nexa_crm_`), refresh cookie (`nexa_crm_refresh`), JWT issuer / audience, export file name, reserved username, email branding.

> Set the name and slug **before the first deployment**. Changing the slug later renames the cookie and the JWT issuer: everybody has to sign in again.

## Step 3 — Configure the backend `.env` ✅

```bash
cp .env.example .env
npm run project:init -- --name "Nexa CRM" --slug nexa-crm --db nexa_crm --reset-secrets
```

`--reset-secrets` writes new random `JWT_ACCESS_SECRET` and `VERIFICATION_TOKEN_SECRET` into `.env`. **Never reuse secrets from another project.**

Then edit `.env`:

### 3.1 Required

| Variable | Set to | Why |
| --- | --- | --- |
| `MONGODB_URI` | `mongodb://localhost:27017/nexa_crm` (local) or your Atlas URI | **A new, empty database.** Two projects must never share one: they would share users. |
| `CORS_ORIGIN` | `http://localhost:5173` (dev), your frontend URL(s) in production | Browser access to the API |
| `JWT_ACCESS_SECRET`, `VERIFICATION_TOKEN_SECRET` | Generated by `--reset-secrets` (or `openssl rand -base64 48`) | Token signing / code hashing; must differ from each other |

### 3.2 Frontend links in emails

| Variable | Example |
| --- | --- |
| `EMAIL_VERIFICATION_URL` | `https://app.nexacrm.com/verify-email` |
| `PASSWORD_RESET_URL` | `https://app.nexacrm.com/reset-password` |
| `INVITE_ACCEPT_URL` | `https://app.nexacrm.com/accept-invite` |
| `FILES_PUBLIC_BASE_URL` | `https://api.nexacrm.com/api/v1/files/public` |

### 3.3 Mail

| Variable | Development | Production |
| --- | --- | --- |
| `MAIL_TRANSPORT` | `outbox` (emails saved as files in `MAIL_OUTBOX_DIR`) | `smtp` |
| `MAIL_FROM` | `Nexa CRM <no-reply@example.com>` | A verified sender of your domain |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD` | — | Your mail provider (set SPF / DKIM / DMARC for the domain) |
| `MAIL_DEFAULT_LANGUAGE` | `en` (or `ta`, `hi`) | Language of invitation emails |

### 3.4 First administrator

| Variable | Set to |
| --- | --- |
| `BOOTSTRAP_ADMIN_EMAIL` | The real admin address of this project (e.g. `admin@nexacrm.com`) |
| `BOOTSTRAP_ADMIN_PASSWORD` | A strong one-time password (the sample `Test@123` is refused in production) |
| `BOOTSTRAP_ADMIN_FIRST_NAME` / `LAST_NAME` | Display name |
| `BOOTSTRAP_ADMIN_MUST_CHANGE_PASSWORD` | `true` (recommended) |

Created on the first start only; changing these values later does not change the account.

### 3.5 Product decisions (review, keep defaults if unsure)

| Topic | Variables |
| --- | --- |
| Sign-up flow | `REGISTRATION_EMAIL_VERIFICATION` (`otp` / `link` / `none`), `REGISTRATION_REQUIRE_APPROVAL` — see [Step 7](#step-7--choose-the-auth-flows-) |
| Sign-in | `LOGIN_IDENTIFIERS` (`email`, `username`), lockout limits, `MAX_SESSIONS_PER_USER` |
| Password reset | `PASSWORD_RESET_METHOD` (`otp` / `link`) |
| Sessions | `JWT_ACCESS_TTL_SECONDS`, `REFRESH_TOKEN_TTL_DAYS`, `REFRESH_TOKEN_REMEMBER_ME_TTL_DAYS`, `REFRESH_TOKEN_DELIVERY` (`cookie` for web, `body` for mobile apps, `both`) |
| Account deletion | `ACCOUNT_DELETION_GRACE_DAYS`, `USER_ACTIVITY_RETENTION_DAYS` |
| Uploads | `UPLOAD_MAX_FILE_SIZE_MB`, `UPLOAD_AVATAR_MAX_SIZE_MB`, `STORAGE_LOCAL_DIR`, `VIRUS_SCAN_ENABLED` (+ `CLAMAV_*`) |
| Security emails | `NEW_DEVICE_ALERTS_ENABLED`, `ACCOUNT_LOCKED_EMAIL_ENABLED` |
| Metrics | `METRICS_ENABLED`, `METRICS_TOKEN` (required in production for scraping) |

Every variable is documented in `.env.example` and in the backend README, section 3.

## Step 4 — Run and check the backend ✅

```bash
npm run build
npm run start:dev
```

Check:

- [ ] `http://localhost:3000/api/v1/health/ready` → `ok` (database, storage).
- [ ] Startup log says `Bootstrap admin created` once.
- [ ] Swagger at `http://localhost:3000/api/docs` shows **"Nexa CRM API"**.
- [ ] Sign in with the bootstrap admin (Swagger `POST /auth/login`), change the password (`PATCH /auth/change-password`).
- [ ] Optional: `npm run test:e2e:build` (runs on its own port and database, never your `.env`).

## Step 5 — Rename and brand the frontend

```bash
cd ../authcore-frontend       # or your renamed folder
npm ci
```

### 5.1 Identity and package name ✅

One command — use the **same name and slug** as the backend:

```bash
npm run project:init -- --name "Nexa CRM" --slug nexa-crm --short-name Nexa \
  --description "Customer relationships, simplified" --color "#0f766e" \
  --company "Nexa Software Pvt Ltd" --support-email support@nexacrm.com \
  --website https://nexacrm.com --language en --timezone Asia/Kolkata
# add --dry-run first to see the changes
```

It updates `src/config/app.config.ts` and the package name (`nexa-crm-frontend` in `package.json` / `package-lock.json`), then prints what is left. The browser title, description, favicon and theme color in `index.html` are filled from `app.config.ts` at build time. Anything else in `app.config.ts` (logos, legal links, theme colors) you edit by hand.

If a value is wrong, the app shows a **Configuration problems** page in development listing each one (production logs them to the console).

### 5.3 Logo and favicon ✅

Replace `public/favicon.svg`. Put logos in `public/brand/` (`logo.svg`, `logo-dark.svg`, `logo-mark.svg` for the collapsed sidebar) and reference them only from `app.config.ts` → `logos` (`light`, `dark`, `mark`); a different favicon file → `favicon`.

### 5.4 Colors and look 🔜

*Frontend module 3 (theme system):* choose a preset or set `brand` in `src/config/theme.config.ts` and the appearance (radius, density, sidebar / navbar style). Until then the color comes from `branding.primaryColor` and the existing components.

### 5.5 Navigation (config ✅, sidebar 🔜)

List your modules in `src/config/navigation.config.ts` (Leads, Contacts, Deals, Reports …), their URLs in `src/config/paths.ts`, and icons in `src/config/icons.ts`. *Frontend module 7 (sidebar)* renders it; items with `status: 'planned'` will show a "not built yet" page.

## Step 6 — Connect the frontend to the backend ✅

```bash
cp .env.example .env
```

| Setting | Development | Production |
| --- | --- | --- |
| `VITE_API_BASE_URL` (`.env`) | `/api/v1` (Vite proxy) | `/api/v1` when the web server proxies `/api` to the backend (recommended), or `https://api.nexacrm.com/api/v1` |
| Proxy target (`vite.config.ts` → `server.proxy`) | `http://localhost:3000` (change if the backend `PORT` differs) | — |

Same origin (proxy) is strongly recommended: the refresh cookie and the backend's origin check then work without extra CORS setup. With separate domains, set `CORS_ORIGIN` to the frontend URL and `REFRESH_COOKIE_SAMESITE` / `REFRESH_COOKIE_SECURE` accordingly.

```bash
npm run dev            # http://localhost:5173
npm run verify         # format, lint, types, architecture rules, build
```

## Step 7 — Choose the auth flows ✅

Backend and frontend must agree. Backend in `.env`, frontend in `src/config/features.config.ts` → `auth`:

| Decision | Backend `.env` | Frontend `features` |
| --- | --- | --- |
| Public sign-up allowed? | Registration endpoint always on; close it at the proxy or keep invites only | `allowRegistration: true / false` |
| Email verification | `REGISTRATION_EMAIL_VERIFICATION=otp | link | none` | `registrationFlow: 'otp' | 'link' | 'none'` |
| Admin approval of new accounts | `REGISTRATION_REQUIRE_APPROVAL=true` | `registrationFlow: 'approval'` |
| Sign in with | `LOGIN_IDENTIFIERS=email,username` | `loginIdentifiers: ['email', 'username']` |
| Remember me | `REFRESH_TOKEN_REMEMBER_ME_TTL_DAYS` | `enableRememberMe` |
| Self account recovery | always available for self-closed accounts | `enableSelfRecovery` |
| Password reset | `PASSWORD_RESET_METHOD=otp | link` | (reset page handles both) |

Typical choices:

| Product | Sign-up | Verification | Approval |
| --- | --- | --- | --- |
| Internal tool / ERP / HRMS | Off (invites only) | — | — |
| B2B CRM | Off or invites | link | optional |
| E-commerce (customers) | On | otp or link | off |
| SaaS self-service | On | link | off |

## Step 8 — Roles, permissions and groups ✅

AuthCore seeds system permissions (users, roles, groups, policies, files, user schema) and three system roles (`ACCESS_CONTROL_ADMIN`, `PASSWORD_POLICY_ADMIN`, `USER_ADMIN`). Add your product's own on top, signed in as the admin (Swagger, Postman or the admin screens once built):

1. **Permissions** for each business action — naming `<RESOURCE>_<ACTION>`:
   `LEAD_READ`, `LEAD_CREATE`, `LEAD_UPDATE`, `LEAD_DELETE`, `DEAL_APPROVE`, `REPORT_EXPORT` (`POST /api/v1/permissions`).
2. **Roles** that bundle them: `SALES_REP`, `SALES_MANAGER`, `SUPPORT_AGENT` (`POST /roles/setup` creates a role with its permissions in one call).
3. **Groups** that hold roles: departments / teams (`POST /groups`, `POST /access-mappings/group-roles`).
4. **Default group** (`isDefault: true`) for what every new user should get (e.g. `ALL_STAFF` with read access).
5. Users join groups (`POST /access-mappings/group-users`, or `groupIds` when creating / inviting users).

In your backend code, protect routes with `@RequirePermissions('LEAD_READ')`; in the frontend, hide UI with `PermissionGate` / `usePermissions()`.

> Want your permissions created automatically on every fresh install? Add them to a small seed (like `access-seed.service.ts`) in your own module instead of creating them by hand per environment.

## Step 9 — Profile fields, password policy, emails ✅

- **Custom user fields** (e.g. `employee_id`, `department`, `customer_tier`): `POST /api/v1/user-schema/attributes` — types, dropdown options, required / unique / internal flags, searchable in the admin user list, optionally in the token.
- **Password policy**: `PUT /api/v1/password-policies` (default: 8–64 chars, upper + lower + digit + special, history 5).
- **Email texts**: `authcore-backend/src/modules/mail/locales/en.locale.ts` (and `ta`, `hi`). Branding (name, color, logo, support line) already comes from `project.config.json`.
- **Languages**: users choose theirs in preferences; add a language by copying a locale file and registering it in `mail-locales.ts`.

## Step 10 — Add your first business module

### Backend ✅

```text
authcore-backend/src/modules/leads/
├── dto/            create-lead.dto.ts, update-lead.dto.ts, lead-query.dto.ts
├── schemas/        lead.schema.ts (extends BaseSchema: UUID ids, timestamps)
├── services/       leads.service.ts
├── leads.controller.ts   @RequirePermissions(...) on every route
└── leads.module.ts       registered in app.module.ts
```

Follow the backend README (architecture and conventions): DTOs for every input, the standard response envelope, `AppException` for errors, `paginate()` for lists, audit-worthy actions logged. `npm run verify` must pass; add an e2e suite in `test/e2e/suites/` if you keep automated backend tests.

If the module stores personal data, add its collection to `user-data-cleanup.service.ts` so permanent account deletion removes it.

### Frontend

```text
authcore-frontend/src/features/leads/      (🔜 target structure, see docs/frontend/folder-structure.md)
├── api/leads.api.ts         calls through the API client only
├── components/              LeadsTable, LeadForm
├── pages/                   LeadsListPage, LeadDetailPage
└── index.ts
```

Add the route (lazy) and the navigation item; protect it with the permission from Step 8.

## Step 11 — CI, Docker and deployment

| Item | Status | What to do |
| --- | --- | --- |
| CI | ✅ | `.github/workflows/backend-ci.yml` and `frontend-ci.yml` run on push / PR. Adjust paths if you renamed folders. |
| Backend image | ✅ | `authcore-backend/Dockerfile`; mount a volume at `/app/uploads`; pass `.env` values as environment variables (never bake `.env` into the image). |
| Frontend hosting | 🔜 | Static `dist/` behind nginx (or any static host) with SPA fallback and `/api` proxied to the backend (frontend Level 3, module 32). |
| HTTPS | — | Required in production: `REFRESH_COOKIE_SECURE=true`, `TRUST_PROXY_HOPS` set to your proxy count. |
| Database | — | Managed MongoDB (replica set), backups per the backend operations notes. |
| Virus scanning | — | `VIRUS_SCAN_ENABLED=true` with a ClamAV container. |
| Monitoring | — | `/api/v1/health/ready` for the load balancer, `/api/v1/metrics` (with `METRICS_TOKEN`) for Prometheus. |
| Postman | optional | Import the OpenAPI spec (`npm run openapi:export`) into a new workspace named after the project. |

## Step 12 — Final checklist

**Identity**

- [ ] Backend `project.config.json` and frontend `app.config.ts` use the same name and slug.
- [ ] No "AuthCore" left in user-facing places: browser title, emails, Swagger title, logos, favicon.
- [ ] Package names changed (`nexa-crm-backend`, `nexa-crm-frontend`).

**Security**

- [ ] New `JWT_ACCESS_SECRET` and `VERIFICATION_TOKEN_SECRET` (not copied from another project).
- [ ] New, empty database.
- [ ] Bootstrap admin email is real; its password changed after the first sign-in.
- [ ] `.env` files not committed; production secrets in the host's secret store.
- [ ] Production: `NODE_ENV=production`, `SWAGGER_ENABLED=false`, `MAIL_TRANSPORT=smtp`, `REFRESH_COOKIE_SECURE=true`, `METRICS_TOKEN` set, `VIRUS_SCAN_ENABLED=true`.

**Behaviour**

- [ ] Auth flows match between backend `.env` and frontend `features` (Step 7).
- [ ] Email links point to the real frontend URLs and open the right pages.
- [ ] Sign-up / sign-in / reset / invite tested end to end with real email delivery (staging).
- [ ] Product roles, permissions and default group created (Step 8).

**Quality**

- [ ] `npm run verify` passes in both apps; CI green.
- [ ] README titles and descriptions updated for the new product.

## What not to change (unless you know why)

| Keep | Reason |
| --- | --- |
| The response envelope and error codes | Frontend API client and error handling rely on them |
| The auth flows' logic (token rotation, lockouts, hashing) | Security-reviewed; configure through `.env` instead |
| System permissions and roles (`isSystem`) | AuthCore's own admin features depend on them; add yours alongside |
| Folder structure and architecture rules | Keeps every project on the same shape, so improvements can move between them |

When you fix a bug or add something generic in a project, consider porting it back to AuthCore so every future project gets it.
